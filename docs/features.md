# Features

How rho-ui behaves, in detail.

The composer's footer holds the session's settings: the permission mode (which tool calls run without asking) on the left, and on the right one button naming the model and reasoning, which opens the model list with search beside the reasoning levels and fast mode. Beside that button, a ring fills as the context window does; hover it for the tokens in use and what the session has cost. New session opens the session right away, so these can be set before the first message; rho writes no file for a session until its first prompt, and the daemon discards an unused draft's session, so nothing is left behind. A setting changed while a turn runs applies when the turn ends.

The app's shortcuts below are written with Ctrl; on macOS, Cmd takes its place, and tooltips show the shortcut this platform uses. The terminal's own keys say how they differ. On macOS the menu bar holds the Rho menu (Settings, Hide, Quit), File (New Session), Edit, View (the sidebar and right panel) and Window (Minimize, Zoom), each with its shortcut; an item is greyed out where it does nothing, such as Copy with no text box or terminal in use. Closing the window quits the app.

A new session (Ctrl+N) starts in the project of the session on screen, else where the last new session started, else `DIR`. Above the draft's composer, "Start a session in" lists your projects, the most recently used first, with the draft's project checked; click one to move the draft there. rho-ui finds no projects on its own: you add them. Type an absolute or `~/` path in the search to browse folders: the list shows the folders the path can go on to (choose one to go into it), and a folder that is there offers Add. Add project… opens the desktop's folder chooser on this machine, and starts the search at `~/` on a remote one. Paste a git URL (`https://…`, `ssh://…`, `git@host:owner/repo`) and the list offers Clone, as does the footer's button in place of Add project…: Enter clones it into the machine's clone folder, adds the clone to your projects, and starts the session there. A URL of a repository the machine already holds lists its checkout instead. A project is a folder, and for a git repository its main checkout, so adding a linked worktree or a subfolder adds the repository it belongs to, and sessions in its worktrees count toward its age. Hover a project and click × (or right-click it) to remove it from the list; its folder stays. rho-ui keeps the list in its [state database](architecture.md#state). Ctrl+Shift+N starts a session with the keyboard in the list's search, which filters by name or path. In a git project, the button beside Add project… chooses where the session works: Local, the project's checkout, or New worktree, a git worktree that the rho daemon adds on a new `rho/…` branch from `HEAD`, so sessions in one repository don't write the same files. Choosing it makes nothing: the worktree is added when the first message goes, so switching back and forth leaves none behind. New sessions start with the last choice, across restarts too; a folder outside git works in Local without forgetting it. The draft's own session, which holds its settings, works in the checkout; the first message opens a session in the new worktree, gives it the draft's settings, and runs there. The daemon owns the worktree: it removes it once it is clean and merged, keeping the branch. `rho worktrees prune` removes those it can now. A session's directory is fixed once it opens, so moving the draft lets its session go and opens another in the new folder: the composer's text stays, and the settings start over from the new session's.

Type `/` at the start of a message, or `$` anywhere in it, and a menu above the composer lists the session's slash commands or skills that start with what you typed. The daemon lists them: rho's own commands it runs (`/compact`, `/init`, `/create-agent`), prompt templates, MCP prompts, workflows and agents, and the skills the session can load. Up and Down move the highlight, Tab completes, and Enter completes unless the name is typed out, or reads as an amount such as `$20`: then Enter sends. Escape closes the menu, without stopping a turn. A completed name goes as typed, and rho runs the command or loads the skill. Commands rho's terminal UI runs itself, such as `/model`, aren't offered.

While a turn runs, its header under the prompt counts up ("Working for 38s"), and says what holds the turn up when the daemon reports it: "compacting the context" while rho compacts it, or why the provider is being asked again and when, as in "rate limited, retrying in 12s". If the provider throws away a reply it was streaming, what had arrived of it leaves the transcript, thoughts and all, and the retry's reply takes its place.

When the agent keeps a plan, "Todo 2 of 5" shows above the composer. It starts folded; a click opens its steps: done steps struck through, the step under way in bold. It scrolls past about seven steps, and goes once every step is done.

While a turn runs, Enter in the composer steers it: the text joins the turn's next model request. Until the model reads it, it waits above the composer, where you can take it back. A message the turn can't take (it waits on an answer, or the daemon had just begun a turn of its own) waits above the composer too, and goes as the next prompt once the turn ends.

When a turn needs you, its request shows in a card above the composer, the oldest first, with a count of any behind it; it takes the keyboard if the composer is empty, so Enter answers. An approval offers Allow once, Allow for this session, and Deny, beside a box for a reason to deny: the tool reads it, and Enter there denies. A plan approval shows the plan and offers each permission mode to carry it out in, and Keep planning, beside a box for feedback that the model reads with whichever you pick. Questions the agent asks, or a subagent asks through its parent, are a questionnaire, one question at a time: pick one choice or several, type an answer of your own where the question takes one, skip an optional question, and submit, or decline them all. A choice the agent suggests is picked already, or marked "suggested" where it only points at it. An answer that doesn't reach the daemon leaves the card as you filled it in. If rho's `[questionnaire] timeout_seconds` is set, a question can come with a fallback: the card counts down to when rho answers it with the agent's fallback answers, and says what they are and why, and the count of requests behind the card counts down to the soonest of theirs. Your first key, paste or click in the card stops its countdown (`rho/session/hold`), and the question waits for you. A question rho answered at its deadline leaves a note in the transcript saying what it answered. The countdown reads the deadline by this machine's clock, so a remote machine's clock that is off shifts it. rho-ui opens its sessions with the questionnaire tool, so their agents can ask.

Each tool call shows the card rho's terminal UI draws for it, which the daemon sends with the call: one line naming the call, such as `read_file(src/main.rs)` or the command it ran, with short facts after it (`32 lines`, `13 matches in 2 files`, `+4 −1`, a nonzero exit). It opens into what the card shows: a search's matches, a command's output, a checklist, an error, an edit's diff. What the call returned to the model and no person needs, such as a whole file it read or an edit's receipt, stays hidden. A diff names its files from the session's workspace, and a diff of one file leaves out its header, as the call's line names the file. While a turn runs, its folded row of steps shows the step running now; opened, the row sums itself up instead, as that step is listed right below.

Messages draw a ` ```mermaid ` block as a diagram and `$$ … $$` or `$ … $` as a formula, in the theme's colors and font, redrawn when the theme or text size changes. Diagrams come from [pele](https://github.com/obsidianmd/pele), Obsidian's Mermaid renderer, run in an embedded QuickJS; formulas from [RaTeX](https://github.com/erweixin/RaTeX). A diagram wider than the transcript scales down to fit. A diagram shows as its code until its closing fence arrives, so a streaming reply doesn't redraw it with every chunk. What can't be drawn stays as written: a diagram pele can't read shows as code, and so does one that takes over 1 s or 64 MiB to draw (rho-ui says so on stderr); a formula RaTeX can't lay out shows as its source, and dollar signs read as prices ("$5 and $10") stay prose.

A paragraph of only images by path, such as `![The loss curve](out/loss.png)`, draws each image at its own size, scaled down to the transcript's width and to 24 rem tall. A relative path is from the session's folder, and the file is read on the session's machine, so a remote session's images come over its ssh connection. Each message reads its images once, so a file rewritten later still shows in an earlier reply as it was then. Images are read one at a time, as each read on a remote machine is a session on its shared ssh connection. An image that can't be shown says so in its place, with its path and why: it isn't a PNG, JPEG, GIF or WebP image, it is over 32 MiB or 4096 px a side (what rho's own `read_file` previews), or it is a web link, which rho-ui doesn't fetch. One that couldn't be read, because the file isn't there yet or the machine didn't answer, is read again when the turn ends, or when clicked. `data:` images are drawn by GPUI Kit's Markdown, as is an image inside a line of text, which Kit shows only from a `data:` URL. Images a tool returns, such as `read_file`'s preview of an image, show as tiles in the call's details.

Click any image, whether in a reply, a tool call or an attachment, to open it at full size in a window over the transcript, with its alt text (or the tool call) under it. It opens fitted to the window, never larger than its own pixels. The bar above it zooms in and out, fits it again, or shows it at 1:1, up to 16 screen pixels to one of the image's; the mouse wheel, a pinch, the platform's zoom modifier with a trackpad scroll, and the keys `+`, `-`, `0` (fit) and `1` (full size) zoom too, around the pointer where there is one, and a double click switches between the fit and full size. Zoomed in, drag the image or scroll a trackpad to move around it. Escape, the close button or a click outside closes it.

Attach any file with the paperclip at the left of the composer's footer, by dropping it on the composer, or by pasting it (Ctrl+V) after copying it in a file manager; paste an image the same way. Each shows above the composer's text: an image as a tile, any other file as a card. An image over 4096 px a side, too large for a texture, shows as a card saying it is too large to preview, with its size, and still goes as an image; so it does in the transcript. When files can't be attached, one alert says why for each. Hover one to remove it, or press Backspace in the empty text box to remove the last. They go with the text as one message, text first, as rho's terminal UI sends them, and the transcript shows them above the message's text.

What goes depends on the file. A PNG, JPEG, GIF or WebP image goes as an image the model sees. A text file of up to 200,000 characters (what the terminal UI sends of a document it attaches) goes whole. Any other file, such as a PDF or a binary, or a longer text file, goes as its path, and the agent reads it with its own tools; its card says "Sent by path", or for a file past a limit, which and by how much, such as "By path: 250000 characters, over the 200000 sent whole". A file over what one message can carry goes by its path unread, and an image whose data doesn't read goes by its path too, saying so. Attachments in one message can come to 16 MiB once encoded, images counting a third more as base64: the daemon reads a message as one line of at most 16 MiB (`rho_protocol::MAX_LINE_BYTES`). A steer carries only text, so a message with attachments sent while a turn runs waits above the composer and goes as the next prompt once the turn ends, and so does any message sent after it.

Background work a session's turns started (processes, workflow runs, subagents) is listed above the composer while it runs, with a button to stop each one. A turn ends while its background work runs on: rho-ui opens sessions with `idle_wake: turn`, so when the work finishes the daemon starts a turn of its own that gives the model the result, and rho-ui shows that turn like any other. Work leaves the list as it ends. A button in the title bar, counting what ended, opens the session's ended work, newest first, with how each piece ended (its exit status, failed, or stopped); it keeps everything rho-ui saw end, after the model has its result and across restarts. The daemon forgets work once the model has its result, so rho-ui records the work it sees start and end. Work it saw running that ended while it was closed shows as ended, with no word on how; work that started and ended while it was closed doesn't show.

Click a subagent's row, in either list, to open the subagent's own session, nested under the session that started it: the title bar reads `project / session / subagent's task`, and a click on any step above the last goes back to it. rho-ui observes the session (`rho/session/observe`) rather than attaching to it, as only the subagent writes there, so the view shows its messages and tool calls as they come, with no composer and no approvals (a subagent's questions go to its parent). A subagent of a subagent nests one step deeper. When the run ends, the parent shows the subagent's whole result as a card, its Markdown rendered and cut to its first 12 lines; Show more under it shows the rest, and Show less folds it again. Any card rho sends, such as a finished command's, shows the same way. Once the run ends, the daemon stops sending its events and the view keeps what it showed; opening the row again reads the session afresh. The sidebar lists only the session at the top, and marks it while one of its subagents is on screen.

The title bar shows the session's project and its title. Branch and other git details are not in it. Click the project to start a new session in it, as Ctrl+N does.

The sidebar lists the daemon's saved sessions. Once a second it also asks the daemon which sessions have work under way, so a session that runs a turn or waits for an approval shows as Working or Needs you whichever client started it. If the daemon refuses to say, the sidebar's footer says why, as it does when the saved sessions can't be listed, until it answers again. A machine whose connection dropped keeps its saved sessions listed; opening, renaming or deleting one says the machine isn't connected, and a rename keeps the old title. A turn that finishes while its session isn't on screen shows Done, in green, until you open the session or it works again. While background work the session's turns started still runs (a subagent, a workflow run, a process), the row says Waiting, by an hourglass, in place of Done; Done shows once that work ends. The daemon's job list names a session's subagents and workflow runs but not its processes, so for a session rho-ui hasn't opened since it started, only those make it wait.

Leave a new session's draft with something in its composer (text or an attachment) and it waits at the top of the sidebar, above pinned sessions, labelled Draft and titled with the message's first line. The one you left most recently is on top. Click it to pick up where you left off: the message, project and settings are as you left them, because the draft keeps its session open in the daemon. Hover it, or right-click it, to discard it. A draft left empty goes, as before. New session on a draft that holds a message leaves that draft in the sidebar and starts a fresh one in the same project. Drafts follow the search and the filter, and last only for this run of the app. A draft survives the daemon reconnecting with its message and project, but its session is opened again, so its settings start over. One whose machine is removed from the settings goes with it.

Right-click a session for its menu: Rename…, Pin or Unpin, Snooze (1 hour, 4 hours or 1 day), Settle or Restore, Copy (the session ID, the `rho -R` command that resumes it, or its folder's path), and Delete…, which a busy session can't do. Rename turns the title into a text box: Enter, or clicking away, saves it in rho (`rho/session/rename`), and Escape leaves it as it was. rho keeps a title you give over one it generates, and refuses a blank one. Pinned sessions lead the list, the latest pinned first, with a pin beside their age; hover one for Unpin. A pinned session can't be settled or snoozed until unpinned.

The button at the top left of the sidebar, or Ctrl+B, collapses it to a narrow rail and opens it again. The rail keeps that button and Settings where they were and puts New session under it. While any session waits for an approval or runs a turn, the rail shows its status icon, so collapsing hides no session that needs you: hover the icon to see how many, and click it to open the sidebar. rho-ui remembers whether the sidebar is collapsed.

Drag the open sidebar's right edge to resize it, no narrower than 14 rem (224px at the default scale) and as far as leaves the session 30 rem beside the right panel; double-click the edge for its default width, 18 rem. rho-ui remembers its width.

The panel at the right of the window holds surfaces, tools that sit beside the session. The toggle at the right end of the title bar, or Ctrl+Alt+B, shows and hides it; while it shows, the toggle sits at the same place in the panel's header. Drag its left edge to resize it, as far as leaves the session 30 rem (480px at the default scale) and no narrower than 16 rem; double-click the edge for its default width, 24 rem. rho-ui remembers whether it shows, and its width. With no surface open, the panel lists the surfaces to open; while one shows, + in its header opens a menu of the rest. Each surface opens as a tab; hover one and × takes the place of its icon to close it. Drag a tab onto another to move it there; tabs that don't fit scroll sideways. The panel belongs to the window, not to a session: its tabs stay as you switch sessions, and each surface shows the session on screen. There are four surfaces so far.

Terminal runs a shell in the session's folder, on the session's machine: on this one, your `$SHELL`; on a remote one, your login shell there, over the ssh connection rho-ui already holds, so it asks nothing. It opens a new tab each time you ask, as many as you like. A tab is named for the program its shell runs, such as `zsh` or `vim`: on this machine the terminal's foreground process (on Linux), on a remote one the title the shell sets, else just Terminal. Right-click a terminal for its menu: Copy, Paste, Split right, Split down, and Close. A split puts a new pane beside or below, each pane with a shell of its own; drag the divider between two panes to resize them. Closing a tab's last pane closes the tab, and a tab is named for the pane last clicked or typed in. Ghostty's keys do the same: Ctrl+Shift+T opens a terminal tab, Ctrl+Page Down and Ctrl+Page Up go to the next and previous one, Ctrl+Shift+O splits right, Ctrl+Shift+E splits down, Ctrl+Shift+W closes the pane, and Ctrl+Alt+arrow moves to the pane that way. On macOS they are Ghostty's Mac keys: Cmd+T, Cmd+Shift+] and Cmd+Shift+[, Cmd+D, Cmd+Shift+D, Cmd+W, and Cmd+Alt+arrow. They act on the terminal you type in, or, while you type elsewhere, the one under the pointer; with neither, the key does what it would anyway, such as Ctrl+Shift+E selecting to the end of the line in a text box. Closing a pane you only point at leaves the keyboard where it is. In each pane, each session has its own shell, started the first time it is on screen there or takes the keyboard, and kept until the pane closes; switching sessions switches shells. Click the terminal to type in it. It takes Tab for the shell rather than the app, and off macOS Ctrl+B, Ctrl+N and Ctrl+C too, where the app's shortcuts use Ctrl; Ctrl+Shift+V pastes (Cmd+V on macOS), the wheel scrolls back through 10,000 lines, and typing returns to the bottom. Drag to select text, double-click for a word, triple-click for a line, and hold Ctrl+Alt while dragging for a rectangle; dragging past the top or bottom scrolls, selecting as it goes. Ctrl+Shift+C (Cmd+C on macOS) copies the selection, and on Linux letting go of the mouse also puts it in the primary selection, which a middle click pastes, in the terminal or elsewhere. Typing clears the selection. A program that asks for the mouse, such as vim, htop, or less with `--mouse`, gets its clicks, drags and wheel instead; hold Shift to select, paste, or open the menu anyway. Input methods work as in any text box: what you compose shows underlined at the cursor, and goes to the shell once you commit it. When the shell on screen exits, as with `exit` or Ctrl+D, its pane closes like a closed pane, even while a job it started in the background still runs, and the tab with its last pane; another session's shell that exits starts afresh the next time that session shows. A shell that couldn't start says why, with Restart to try again. Ghostty's terminal core, libghostty-vt 1.0.1, keeps the screen, encodes keys and the mouse, and finds what a click selects; rho-ui draws it in the theme's code font and colors.

Files lists the session's folder as a tree, folders first, each by name. In a git repository it lists what git sees: tracked files that are there, and untracked files that `.gitignore` doesn't leave out; outside one, every file under the folder. Click a folder to open or shut it, and a file to read it in place of the tree, read-only, its syntax highlighted by its extension, with line numbers; Back returns to the tree as you left it. A file over 2 MiB, or one holding a NUL (git's test for binary), shows a note instead. The list stops at 8 MiB of paths, and says so. Like Diff, it reads the files on the session's machine, again when another session comes on screen, when the session's turn ends, and on Refresh, and reads the open file again with them; a read that finds the same leaves the view where it was scrolled.

Diff shows the uncommitted changes in the repository the session works in: every change to tracked files against `HEAD`, staged or not, and each untracked file that `.gitignore` doesn't leave out, as a new file, with how many files changed and lines added and removed, and each file's own count in its header. Long lines wrap to the panel's width. It runs `git` on the session's machine, over the ssh connection for a remote one, and reads the changes again when another session comes on screen, when the session's turn ends, and on Refresh; a read that finds the same changes leaves the view where it was scrolled. Changes made during a turn show once it ends, or on Refresh. A folder outside any git repository says so. Diff shows at most 8 MiB of changes: past that it shows the whole files that fit and says where it stopped. A pull request's diff is for later, with GitHub's `gh`.

Background work lists the session's running work, each with a button to stop it, then what ended, newest first, as the title bar's list does; a subagent's row opens its session.

Pinning, settling and snoozing sessions is rho-ui's own idea; rho has no such state. Sessions started or continued in rho-ui list as active. Sessions from elsewhere, such as rho's terminal UI, start out settled, so the sidebar doesn't fill with old history; a session with work under way always lists as active, and pinning, snoozing, restoring, prompting, or steering one makes it rho-ui's. rho-ui keeps this in its [state database](architecture.md#state). A settled session comes back when it has new activity in rho-ui, and a snoozed one when its time is up. Snoozed and Settled sit under the active sessions, folded; open one to see its sessions on one line each, and hover a session for its details. An opened shelf shows its newest 25 sessions; Show more under them adds 25 more each time, and folding the shelf goes back to 25.

Settings (Ctrl+, or the gear at the bottom of the sidebar) open in a dialog over the window and hold the theme, the UI scale, the UI font (default Noto Sans) and the code font (default JetBrainsMono Nerd Font), saved in `$XDG_CONFIG_HOME/rho-ui/settings`. The theme is dark by default, or light, or whichever the desktop uses (System), following it as it changes. System isn't the default because on Linux rho-ui starts before the desktop portal reports light or dark, so a dark desktop would see a light first frame, and a desktop with no portal would stay light. Both themes are rho-ui's own, in `crates/rho-ui/themes/rho-ui.json` (GPUI Kit's theme format), in place of Kit's stock ones.

After rho-ui's own pages comes rho's: one page with a group for each category of settings rho's daemon describes (`rho/config/schema`), in its order, each listed under it in the sidebar, saved in that machine's `~/.rho/config.toml`. rho-ui draws them from the daemon's description alone, so a setting a newer rho adds shows up with no change to rho-ui. Each item is the setting's name, what it does and when a change applies (from the next turn, to new sessions, or once rho restarts), with a control for its kind: a switch, a dropdown of its choices, a number box held to its range with its unit, or a text box. Number and text boxes apply on Enter or when they lose the keyboard; an empty one resets the setting. A model setting shows its model, which `/config` in rho's terminal UI changes, and a kind rho-ui doesn't know is left out. A setting your file sets can go back to its default with the page's reset button. A change applies at once and shows at once; rho-ui sends one write at a time to each machine. If someone else changed the settings since rho-ui read them, in rho's terminal UI or by hand, rho refuses the write: the page says your change didn't land and shows the settings as they are now. Changes made elsewhere show up on an open page as they happen. When `config.toml` doesn't load, the page says why, beside the setting it names, and rho uses the last values that loaded.

Every machine's rho has its own `config.toml`. With remote machines, a Machine picker heads rho's page, set to this machine when Settings opens; picking another shows that machine's settings. A machine that is connecting or can't be reached says so in place of its settings.

Last comes About: rho-ui's version, a link to its source and its license, then the version of Rho on each machine, or that it is connecting or can't be reached, with what that machine's rho needs under it, as the sidebar offers it (see [Installing and updating rho](#installing-and-updating-rho)).

rho-ui's own settings stay in its own file, not in rho's: the theme, scale and fonts must apply before the first frame, before any daemon answers, and the machines list is how rho-ui finds the remote daemons in the first place.

## Installing and updating rho

rho-ui checks each machine's rho when it connects to it, or fails to, by running `rho update --check --json` there, over ssh for a remote machine. A check that found rho is good for an hour, since each one asks GitHub, which allows 60 requests an hour from one address without a login. A `rho` given as plain `rho` that isn't on `PATH` falls back to `~/.local/bin/rho`, where rho's install script puts it, since a desktop session's or an ssh command's `PATH` often lacks that folder.

- No rho on this machine, and so no daemon to connect to: the main pane offers Install Rho in place of the connection's error, which runs rho's install script (`https://matthewyjiang.github.io/rho/install.sh`) into `~/.local/bin`, or into the folder of a `--rho` path, then connects. A remote machine without rho gets the same offer at the bottom of the sidebar, into the folder of its rho path in Settings. A machine whose daemon answers has rho, wherever the check looked, so it is never offered an install.
- A newer release: the sidebar's footer says so with Update, which runs `rho update`, so rho installs it the way it was installed. When that needs a terminal, as pacman's `sudo` does, the footer shows the command to copy instead.
- After an update, the daemon still runs the old rho until nothing would be cut short. While it waits on work, the footer says how many things it waits for, with Restart now. rho-ui asks the daemon about a waiting upgrade when its jobs change, at once after it updates rho, and otherwise every 30 seconds, since the daemon's status reads its credential store each time. That restarts the daemon at once, stopping its background processes. Once it is back, rho-ui opens the session that was on screen again and attaches for a moment to every other session it had open with work under way: rho carries on a turn the restart cut short when a client that takes turns the daemon starts attaches to its session again. Sessions other clients follow, such as rho's terminal UI, are theirs to carry on.

A rho from before `rho update --check` can't say whether a newer one is out, so rho-ui offers nothing for it; update it once with `rho update`.

## Machines

rho-ui shows the sessions of several machines side by side: this one, and any remote machine you add on the Machines page of Settings by its SSH host, such as a host in `~/.ssh/config`. rho-ui reaches a remote machine over ssh, starts its daemon there if none runs, and runs its sessions with that machine's login environment. ssh can't ask for a password in the app: the host must be in `known_hosts`, and your key must sign without a terminal prompt, as an SSH agent does. With 1Password's agent you approve the key once; rho-ui keeps one ssh connection per machine for ten minutes after its last use, so a retry or reconnect asks nothing. A remote machine whose `rho` isn't on the `PATH` of an ssh command gets its rho path set on the same page, as an absolute or `~/` path. Each machine also has a clone folder there, where the project list clones repositories. Each machine has a name, set there too (this machine's is `local` until you change it; a remote one shows its host until named).

The sidebar lists every machine's sessions in one list, newest first, and with more than one machine each active row names its machine's label; a snoozed or settled row leaves it to the card its hover shows. The filter beside the search hides machines, or keeps to the projects you choose. A machine rho-ui can't reach shows at the bottom of the sidebar with ssh's or rho's reason and a Retry button; the others work on. A link that dies, as when the laptop sleeps or changes networks, shows there within about 45 seconds, when ssh's keepalives give up. A login shell that hasn't printed its environment within 30 seconds fails the connection too.

A remote machine needs a few things of its server:

- sshd must allow forwarding to a Unix socket, since rho-ui reaches the daemon with `ssh -W`. `AllowStreamLocalForwarding no` or `DisableForwarding yes` in `sshd_config` refuses it.
- The login shell must take `-l -c`. bash, zsh, fish and sh do; csh and tcsh may not.
- rho-ui starts the daemon from its ssh connection. Where systemd-logind has `KillUserProcesses=yes`, the daemon dies with that connection, ten minutes after rho-ui last used it; run `loginctl enable-linger` there, or start the daemon some other way.
- The daemon's home comes from `RHO_HOME` as an ssh command sees it, not as a login shell does. Set it in a file a non-login shell reads, such as `~/.zshenv`, if you move it.

A project is one repository, however many machines hold a checkout of it and whatever branch each is on. With more than one machine, the button in the project list's footer chooses the machine the session runs on: the list shows each project's checkout there, and a project with no checkout there shows where it is, with Clone to that machine: choosing it clones the repository from its origin remote into the machine's clone folder and starts the session in the clone. A project outside git, which has nothing to clone, shows dimmed, and choosing it looks for the same path on the chosen machine. Right-clicking either removes it. Each machine's clone folder is set on the Machines page; empty means `$RHO_HOME/projects` on that machine, and a relative path is from its home. git never prompts during a clone: a repository that needs a password, or a host key not yet known, fails with git's message, so the machine needs its own key for a private repository. A folder that already holds a clone of the same URL is taken as it is, once it has a commit; one a clone cut short left is refused as incomplete. Switching machines moves the draft to its project's checkout on the new one, else to that machine's home folder; a machine that isn't connected can't be chosen. Projects match by repository name without its owner, or by folder name outside git, so forks and same-named folders count as one. A typed path on a remote machine is browsed over the ssh connection to its daemon, once typing pauses; if its folders can't be read, the list says why and offers nothing to add. A file that would go by its path can't be attached to a message for a remote machine, and the refusal says why it would, such as its size over a limit: send text files and images there instead. A remote workspace's project name and branch come from running `git` there, over the ssh connection to its daemon, while it is connected; without `git` on that machine's `PATH` they show the folder's name and no branch. If its repositories can't be read, the sidebar's footer says why.
