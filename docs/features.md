# Features

How rho-ui behaves, in detail.

The composer's footer holds the session's settings: the permission mode (which tool calls run without asking) on the left, and on the right one button naming the model and reasoning, which opens the model list with search beside the reasoning levels and fast mode. Beside that button, a ring fills as the context window does; hover it for the tokens in use and what the session has cost. New session opens the session right away, so these can be set before the first message; rho writes no file for a session until its first prompt, and the daemon discards an unused draft's session, so nothing is left behind. A setting changed while a turn runs applies when the turn ends.

The app's shortcuts below are written with Ctrl; on macOS, Cmd takes its place, and tooltips show the shortcut this platform uses. The terminal's own keys say how they differ. On macOS the menu bar holds the Rho menu (Settings, Hide, Quit), File (New Session), Edit, View (the sidebar and right panel) and Window (Minimize, Zoom), each with its shortcut; an item is greyed out where it does nothing, such as Copy with no text box or terminal in use. Closing the window quits the app.

A new session (Ctrl+N) starts in the project of the session on screen, else where the last new session started, else `DIR`. Above the draft's composer, "Start a session in" lists your projects, the most recently used first, with the draft's project checked; click one to move the draft there. rho-ui finds no projects on its own: you add them. Type an absolute or `~/` path in the search to browse folders, by the rules of the draft's machine (on Windows, `C:\code` or `~\code` here; a remote machine's paths are POSIX ones, such as `/srv/app`): the list shows the folders the path can go on to (choose one to go into it), and a folder that is there offers Add. Add project… opens the desktop's folder chooser on this machine, and starts the search at `~/` on a remote one. Paste a git URL (`https://…`, `ssh://…`, `git@host:owner/repo`) and the list offers Clone, as does the footer's button in place of Add project…: Enter clones it into the machine's clone folder, adds the clone to your projects, and starts the session there. A URL of a repository the machine already holds lists its checkout instead. A project is a folder, and for a git repository its main checkout, so adding a linked worktree or a subfolder adds the repository it belongs to, and sessions in its worktrees count toward its age. Hover a project and click × (or right-click it) to remove it from the list; its folder stays. rho-ui keeps the list in its [state database](architecture.md#state). Ctrl+Shift+N starts a session with the keyboard in the list's search, which filters by name or path. In a git project, the button beside Add project… chooses where the session works: Local, the project's checkout, or New worktree, a git worktree that the rho daemon adds on a new `rho/…` branch from `HEAD`, so sessions in one repository don't write the same files. Choosing it makes nothing: the worktree is added when the first message goes, so switching back and forth leaves none behind. New sessions start with the last choice, across restarts too; a folder outside git works in Local without forgetting it. The draft's own session, which holds its settings, works in the checkout; the first message opens a session in the new worktree, gives it the draft's settings, and runs there. The daemon owns the worktree: it removes it once it is clean and merged, keeping the branch. Settings → Worktrees, or `rho worktrees prune`, removes those it can now. A session's directory is fixed once it opens, so moving the draft lets its session go and opens another in the new folder: the composer's text stays, and the settings start over from the new session's.

Type `/` at the start of a message, or `$` anywhere in it, and a menu above the composer lists the session's slash commands or skills that start with what you typed. The daemon lists them: rho's own commands it runs (`/compact`, `/init`, `/create-agent`), prompt templates, MCP prompts, workflows and agents, and the skills the session can load. To run a new session as one of the workspace's agents, make its first message `/agent:<name>` and the task: rho binds the session to that agent, which takes over its settings, and runs the task. Up and Down move the highlight, Tab completes, and Enter completes unless the name is typed out, or reads as an amount such as `$20`: then Enter sends. Escape closes the menu, without stopping a turn. A completed name goes as typed, and rho runs the command or loads the skill. Commands rho's terminal UI runs itself, such as `/model`, aren't offered.

While a turn runs, its header under the prompt counts up ("Working for 38s"), and says what holds the turn up when the daemon reports it: "compacting the context" while rho compacts it, or why the provider is being asked again and when, as in "rate limited, retrying in 12s". If the provider throws away a reply it was streaming, what had arrived of it leaves the transcript, thoughts and all, and the retry's reply takes its place.

When the agent keeps a plan, "Todo 2 of 5" shows above the composer. It starts folded; a click opens its steps: done steps struck through, the step under way in bold. It scrolls past about seven steps, and goes once every step is done.

While a turn runs, Enter in the composer steers it: the text joins the turn's next model request. Until the model reads it, it waits above the composer, where you can take it back. Once read, it shows in the transcript as a turn of its own, as it will when the session replays (rho's replay doesn't mark steers): the work before it folds behind "Worked for", and the header under the steer counts up from there, while the sidebar counts the whole job. rho's attach doesn't say when a steer applied either, so a session reopened mid-turn counts the steer's header from the turn's start. A message the turn can't take (it waits on an answer, or the daemon had just begun a turn of its own) waits above the composer too, and goes as the next prompt once the turn ends.

When a turn needs you, its request shows in a card above the composer, the oldest first, with a count of any behind it; it takes the keyboard if the composer is empty, so Enter answers. An approval offers Allow once, Allow for this session, and Deny, beside a box for a reason to deny: the tool reads it, and Enter there denies. A plan approval shows the plan and offers each permission mode to carry it out in, and Keep planning, beside a box for feedback that the model reads with whichever you pick. Questions the agent asks, or a subagent asks through its parent, are a questionnaire, one question at a time: pick one choice or several, type an answer of your own where the question takes one, skip an optional question, and submit, or decline them all. A choice the agent suggests is picked already, or marked "suggested" where it only points at it. An answer that doesn't reach the daemon leaves the card as you filled it in. If rho's `[questionnaire] timeout_seconds` is set, a question can come with a fallback: the card counts down to when rho answers it with the agent's fallback answers, and says what they are and why, and the count of requests behind the card counts down to the soonest of theirs. Your first key, paste or click in the card stops its countdown (`rho/session/hold`), and the question waits for you. A question rho answered at its deadline leaves a note in the transcript saying what it answered. The countdown reads the deadline by this machine's clock, so a remote machine's clock that is off shifts it. rho-ui opens its sessions with the questionnaire tool, so their agents can ask.

Each tool call shows the card rho's terminal UI draws for it, which the daemon sends with the call: one line naming the call, such as `read_file(src/main.rs)` or the command it ran, with short facts after it (`32 lines`, `13 matches in 2 files`, `+4 −1`, a nonzero exit). It opens into what the card shows: a search's matches, a command's output, a checklist, an error, an edit's diff. What the call returned to the model and no person needs, such as a whole file it read or an edit's receipt, stays hidden. A diff names its files from the session's workspace, and a diff of one file leaves out its header, as the call's line names the file. While a turn runs, its folded row of steps shows the step running now; opened, the row sums itself up instead, as that step is listed right below.

A code block in a message or a notice names its language in its top corner, beside a button that copies its code in one click; the button shows a check for 2 seconds after.

Drag to select a message's text, across messages too, and copy it with Ctrl+C. A long reply is drawn in stretches of about 2,000 characters, which shows in two places: Select All (Ctrl+A) in it selects the stretch you clicked in, not the whole reply, and a selection is dropped once the stretch it started in is scrolled well off screen.

Letting go of a drag that selected text in the transcript, or a double click on a word, shows an Add to prompt button just above the pointer. It quotes the selection above the composer's text box, not in it, and puts the keyboard in the box. Quote several passages and each shows, muted, up to three lines, with a button to remove it. They go before the text as Markdown block quotes, the first added first (after a slash command, which rho runs only from a prompt's start), so the transcript shows the sent message with them quoted. The button goes with a click elsewhere or once you scroll the transcript. A send that fails gives the message back as text, quotes and all, in the text box.

Messages, and a PR's description and posts in the Pull request surface, draw a ` ```mermaid ` block as a diagram and `$$ … $$` or `$ … $` as a formula, in the theme's colors and font, redrawn when the theme or text size changes. Diagrams come from [pele](https://github.com/obsidianmd/pele), Obsidian's Mermaid renderer, run in an embedded QuickJS; formulas from [RaTeX](https://github.com/erweixin/RaTeX). A diagram wider than its column scales down to fit. A diagram shows as its code until its closing fence arrives, so a streaming reply doesn't redraw it with every chunk. As anyone who can comment on a PR writes its text, a PR's diagrams are drawn in the background, on a pele of their own, only while its tab shows; each shows as code until it is drawn, and of a PR's different diagrams, the first 20 are drawn, its description's first, and the rest show as code (rho-ui says so on stderr). What can't be drawn stays as written: a diagram pele can't read shows as code, and so does one that takes over 1 s or 64 MiB to draw (rho-ui says so on stderr); a formula RaTeX can't lay out shows as its source, and dollar signs read as prices ("$5 and $10") stay prose.

A paragraph of only images by path, such as `![The loss curve](out/loss.png)`, draws each image at its own size, scaled down to the transcript's width and to 24 rem tall. A relative path is from the session's folder, and the file is read on the session's machine, so a remote session's images come over its ssh connection. Each message reads its images once, so a file rewritten later still shows in an earlier reply as it was then. Images are read one at a time, as each read on a remote machine is a session on its shared ssh connection. An image that can't be shown says so in its place, with its path and why: it isn't a PNG, JPEG, GIF or WebP image, it is over 32 MiB or 4096 px a side (what rho's own `read_file` previews), or it is a web link, which rho-ui doesn't fetch. One that couldn't be read, because the file isn't there yet or the machine didn't answer, is read again when the turn ends, or when clicked. `data:` images are drawn by GPUI Kit's Markdown, as is an image inside a line of text, which Kit shows only from a `data:` URL. Images a tool returns, such as `read_file`'s preview of an image, show as tiles in the call's details.

Click any image, whether in a reply, a tool call or an attachment, to open it at full size in a window over the transcript, with its alt text (or the tool call) under it. It opens fitted to the window, never larger than its own pixels. The bar above it zooms in and out, fits it again, or shows it at 1:1, up to 16 screen pixels to one of the image's; the mouse wheel, a pinch, the platform's zoom modifier with a trackpad scroll, and the keys `+`, `-`, `0` (fit) and `1` (full size) zoom too, around the pointer where there is one, and a double click switches between the fit and full size. Zoomed in, drag the image or scroll a trackpad to move around it. Escape, the close button or a click outside closes it.

Attach any file with the paperclip at the left of the composer's footer, by dropping it on the composer, or by pasting it (Ctrl+V) after copying it in a file manager; paste an image the same way. Each shows above the composer's text: an image as a tile, any other file as a card. An image over 4096 px a side, too large for a texture, shows as a card saying it is too large to preview, with its size, and still goes as an image; so it does in the transcript. When files can't be attached, one alert says why for each. Hover one to remove it, or press Backspace in the empty text box to remove the last. They go with the text as one message, text first, as rho's terminal UI sends them, and the transcript shows them above the message's text.

What goes depends on the file. A PNG, JPEG, GIF or WebP image goes as an image the model sees. A text file of up to 200,000 characters (what the terminal UI sends of a document it attaches) goes whole. Any other file, such as a PDF or a binary, or a longer text file, goes as its path, and the agent reads it with its own tools; its card says "Sent by path", or for a file past a limit, which and by how much, such as "By path: 250000 characters, over the 200000 sent whole". A file over what one message can carry goes by its path unread, and an image whose data doesn't read goes by its path too, saying so. Attachments in one message can come to 16 MiB once encoded, images counting a third more as base64: the daemon reads a message as one line of at most 16 MiB (`rho_protocol::MAX_LINE_BYTES`). A steer carries only text, so a message with attachments sent while a turn runs waits above the composer and goes as the next prompt once the turn ends, and so does any message sent after it.

A session whose model has no credentials on its machine still opens: rho-ui opens sessions with `sign_in: later`, as rho's terminal UI does, where rho would otherwise refuse to open one. A card above its composer says the model's auth profile isn't signed in, and signs it in there. A profile that takes an API key has a masked box for it, which Save or Enter sends to the daemon: the provider checks it, and a key it refuses is saved nowhere, with the provider's reason under the box; the box empties either way, so the key doesn't stay on screen. A profile that takes an account's login has Sign in, which starts the login in the daemon (see Providers below). Once the profile is signed in, the card goes. The composer still sends while it shows: a message sent signed out fails, saying why. A key the provider couldn't check, as a custom provider's or one behind a gateway that lists no models, is saved and signs the profile in, but may be wrong, so the card stays to say so, with a box to enter it again, until dismissed. The card follows the model, so switching to a model that is signed in makes it go too. rho tells nothing of a sign-out made elsewhere, as in rho's terminal UI, until a turn fails for it: when a turn fails, rho-ui asks again, and the card comes back if the profile is now signed out.

Background work a session's turns started (processes, workflow runs, subagents) is listed above the composer while it runs, with a button to stop each one. A turn ends while its background work runs on: rho-ui opens sessions with `idle_wake: turn`, so when the work finishes the daemon starts a turn of its own that gives the model the result, and rho-ui shows that turn like any other. Work leaves the list as it ends. A button in the title bar, counting what ended, opens the session's ended work, newest first, with how each piece ended (its exit status, failed, or stopped); it keeps everything rho-ui saw end, after the model has its result and across restarts. The daemon forgets work once the model has its result, so rho-ui records the work it sees start and end. Work it saw running that ended while it was closed shows as ended, with no word on how; work that started and ended while it was closed doesn't show. The daemon's job list, which rho-ui reads once a second, adds what the session's own list lacks: a queued subagent or workflow run says where it waits in line, a failed one says why under its row, and a run that ended while rho-ui was closed says how, from the daemon's record of it.

Click a subagent's row, in either list, to open the subagent's own session, nested under the session that started it: the title bar reads `project / session / subagent's task`, and a click on any step above the last goes back to it. rho-ui observes the session (`rho/session/observe`) rather than attaching to it, as only the subagent writes there, so the view shows its messages and tool calls as they come, with no composer and no approvals (a subagent's questions go to its parent). A subagent of a subagent nests one step deeper. When the run ends, the parent shows the subagent's whole result as a card, its Markdown rendered and cut to its first 12 lines; Show more under it shows the rest, and Show less folds it again. Any card rho sends, such as a finished command's, shows the same way. Once the run ends, the daemon stops sending its events and the view keeps what it showed; opening the row again reads the session afresh. The sidebar lists only the session at the top, and marks it while one of its subagents is on screen.

The title bar shows the session's project and its title. Branch and other git details are not in it. Click the project to start a new session in it, as Ctrl+N does.

The sidebar lists the daemon's saved sessions. Once a second it also asks the daemon which sessions have work under way, so a session that runs a turn or waits for an approval shows as Working or Needs you whichever client started it. If the daemon refuses to say, the sidebar's footer says why, as it does when the saved sessions can't be listed, until it answers again. A machine whose connection dropped keeps its saved sessions listed; opening, renaming or deleting one says the machine isn't connected, and a rename keeps the old title. A turn that finishes while its session isn't on screen shows Done, in green, until you open the session or it works again. While background work the session's turns started still runs (a subagent, a workflow run, a process), the row says Waiting, by an hourglass, in place of Done; Done shows once that work ends. The daemon's job list names a session's subagents and workflow runs but not its processes, so for a session rho-ui doesn't follow (see below), only those make it wait.

Leave a new session's draft with something in its composer (text or an attachment) and it waits at the top of the sidebar, above pinned sessions, labelled Draft and titled with the message's first line. The one you left most recently is on top. Click it to pick up where you left off: the message, project and settings are as you left them, because the draft keeps its session open in the daemon. Hover it, or right-click it, to discard it. A draft left empty goes, as before. New session on a draft that holds a message leaves that draft in the sidebar and starts a fresh one in the same project. Drafts follow the search and the filter, and last only for this run of the app. A draft survives the daemon reconnecting with its message and project, but its session is opened again, so its settings start over. One whose machine is removed from the settings goes with it.

A session's title bar has a folder button that lists the directories its tools reach besides its workspace, with their count once there are any. Type a path in its box, absolute or under `~/` by the rules of the session's machine, and Enter or Add adds it: rho saves it with the session and tells the model from its next turn on. A path rho refuses, such as one that isn't a directory, says why under the box and stays there to fix. Added while a turn runs, it waits for the turn to end, as a settings change does. A subagent's session only lists its directories.

rho-ui follows a session while it is on screen, and while it has something under way: a turn, a request waiting for you, background work or its result not yet given to the model, a message being sent, or something typed in its composer, its directory box or its sign-in key box. Once a session you left has none of these, rho-ui lets it go, so the daemon can unload it; its row stays, Done and all, and follows the daemon's jobs. Opening it again replays it from the daemon, which for the largest sessions takes a fraction of a second; where it was scrolled to isn't kept. A saved session shows "Loading session…" until its replay has all arrived, then opens at its end, drawn once rather than growing as the history arrives; its composer sends from then on. A subagent's session goes with the session above it.

Right-click a session for its menu: Rename…, Pin or Unpin, Snooze (1 hour, 4 hours or 1 day), Settle or Restore, Copy (the session ID, the `rho -R` command that resumes it, or its folder's path), and Delete…, which a busy session can't do. Rename turns the title into a text box: Enter, or clicking away, saves it in rho (`rho/session/rename`), and Escape leaves it as it was. rho keeps a title you give over one it generates, and refuses a blank one. Pinned sessions lead the list, the latest pinned first, with a pin beside their age; hover one for Unpin. A pinned session can't be settled or snoozed until unpinned.

The button at the top left of the sidebar, or Ctrl+B, collapses it to a narrow rail and opens it again. The rail keeps that button and Settings where they were and puts New session under it. While any session waits for an approval or runs a turn, the rail shows its status icon, so collapsing hides no session that needs you: hover the icon to see how many, and click it to open the sidebar. rho-ui remembers whether the sidebar is collapsed.

Drag the open sidebar's right edge to resize it, no narrower than 14 rem (224px at the default scale) and as far as leaves the session 30 rem beside the right panel; double-click the edge for its default width, 18 rem. rho-ui remembers its width.

The panel at the right of the window holds surfaces, tools that sit beside the session. The toggle at the right end of the title bar, or Ctrl+Alt+B, shows and hides it; while it shows, the toggle sits at the same place in the panel's header. Drag its left edge to resize it, as far as leaves the session 30 rem (480px at the default scale) and no narrower than 16 rem; double-click the edge for its default width, 24 rem. rho-ui remembers whether it shows, and its width. With no surface open, the panel lists the surfaces to open; while one shows, + in its header opens a menu of the rest. Each surface opens as a tab; hover one and × takes the place of its icon to close it. Drag a tab onto another to move it there; tabs that don't fit scroll sideways. Each session has its own tabs: switching sessions switches to that session's, and a session on screen for the first time has none open. A session's tabs live on while another shows, its terminals' shells too, until rho-ui quits. With no session on screen, as on a draft, the panel has no tabs. There are five surfaces so far.

Terminal runs a shell in the session's folder, on the session's machine: on this one, your `$SHELL`; on a remote one, your login shell there, under a pseudo-terminal sshd makes, over an ssh connection of rho-ui's own that the machine's terminals share, so this machine needs no `ssh` program, and your key agent asks once more, for the first terminal there, not for each. It is told it is an `xterm-256color`, and gets `COLORTERM=truecolor` and this machine's locale (`LANG` and `LC_*`, as a `SendEnv LANG LC_*` in your ssh config would send them) where the host's `AcceptEnv` lets them through. sshd hands the command that starts it, `cd` into the folder then `exec "$SHELL" -l`, to your login shell there, so that shell must read POSIX quoting (sh, bash and zsh do; with fish, a folder whose name holds a backslash goes wrong). It opens a new tab each time you ask, as many as you like. A tab is named for the program its shell runs, such as `zsh` or `vim`: on this machine the terminal's foreground process (on Linux), on a remote one the title the shell sets, else just Terminal. Right-click a terminal for its menu: Copy, Paste, Split right, Split down, and Close. A split puts a new pane beside or below, each pane with a shell of its own; drag the divider between two panes to resize them. Closing a tab's last pane closes the tab, and a tab is named for the pane last clicked or typed in. Ghostty's keys do the same: Ctrl+Shift+T opens a terminal tab, Ctrl+Page Down and Ctrl+Page Up go to the next and previous one, Ctrl+Shift+O splits right, Ctrl+Shift+E splits down, Ctrl+Shift+W closes the pane, and Ctrl+Alt+arrow moves to the pane that way. On macOS they are Ghostty's Mac keys: Cmd+T, Cmd+Shift+] and Cmd+Shift+[, Cmd+D, Cmd+Shift+D, Cmd+W, and Cmd+Alt+arrow. They act on the terminal you type in, or, while you type elsewhere, the one under the pointer; with neither, the key does what it would anyway, such as Ctrl+Shift+E selecting to the end of the line in a text box. Closing a pane you only point at leaves the keyboard where it is. A terminal tab belongs to its session, like every tab, so its shells run in that session's folder. Click the terminal to type in it. It takes Tab for the shell rather than the app, and off macOS Ctrl+B, Ctrl+N and Ctrl+C too, where the app's shortcuts use Ctrl; Ctrl+Shift+V pastes (Cmd+V on macOS), the wheel scrolls back through 10,000 lines, and typing returns to the bottom. Drag to select text, double-click for a word, triple-click for a line, and hold Ctrl+Alt while dragging for a rectangle; dragging past the top or bottom scrolls, selecting as it goes. Ctrl+Shift+C (Cmd+C on macOS) copies the selection, and on Linux letting go of the mouse also puts it in the primary selection, which a middle click pastes, in the terminal or elsewhere. Typing clears the selection. A program that asks for the mouse, such as vim, htop, or less with `--mouse`, gets its clicks, drags and wheel instead; hold Shift to select, paste, or open the menu anyway. Input methods work as in any text box: what you compose shows underlined at the cursor, and goes to the shell once you commit it. When the shell on screen exits, as with `exit` or Ctrl+D, its pane closes like a closed pane, even while a job it started in the background still runs, and the tab with its last pane, also while another session is on screen. A shell that couldn't start says why, with Restart to try again; so does a remote shell whose connection drops. The terminals' connection is apart from the one rho-ui's own reads of the machine use (the Files, Diff and Pull request surfaces, pictures, git), so they never take each other's ssh sessions. A remote machine runs at most 10 terminal shells at once, the sessions sshd allows on a connection by default (`MaxSessions`); an eleventh doesn't start, and says so: exit a shell there, or close a pane, which keeps a shell for each of the machine's sessions it has shown. Closing a pane hangs up on its shells at once. An open remote terminal keeps the terminals' connection open: the 10 minutes it lingers start once the last terminal there goes. Ghostty's terminal core, libghostty-vt 1.0.1, keeps the screen, encodes keys and the mouse, and finds what a click selects; rho-ui draws it in the theme's code font and colors.

Files lists the session's folder as a tree, folders first, each by name. In a git repository it lists what git sees: tracked files that are there, and untracked files that `.gitignore` doesn't leave out; outside one, every file under the folder. Click a folder to open or shut it, and a file to read it in place of the tree, read-only, its syntax highlighted by its extension, with line numbers; Back returns to the tree as you left it. A file over 2 MiB, or one holding a NUL (git's test for binary), shows a note instead. The list stops at 8 MiB of paths, and says so. Like Diff, it reads the files on the session's machine, again when its session comes back on screen, when its turn ends, and on Refresh, and reads the open file again with them; a read that finds the same leaves the view where it was scrolled.

Diff shows the uncommitted changes in the repository the session works in: every change to tracked files against `HEAD`, staged or not, and each untracked file that `.gitignore` doesn't leave out, as a new file, with how many files changed and lines added and removed, and each file's own count in its header. Long lines wrap to the panel's width. It runs `git` on the session's machine, over the ssh connection for a remote one, and reads the changes again when its session comes back on screen, when its turn ends, and on Refresh; a read that finds the same changes leaves the view where it was scrolled. Changes made during a turn show once it ends, or on Refresh. A folder outside any git repository says so. Diff shows at most 8 MiB of changes: past that it shows the whole files that fit and says where it stopped. A pull request's diff is for later, with GitHub's `gh`.

Pull request shows the pull request whose head is the branch the session works on, in a repository whose origin is on GitHub: whether it is open, a draft, merged or closed, its number and title, its author and branches, the lines it adds and removes and the files it touches, whether its review approved it, its checks with the ones that failed first (a click opens one's log; the first 50 show, with how many more there are), and its description. Under them are its comment threads on the code, each under its file and line, open ones open and resolved ones closed until clicked; then its conversation: its comments and reviews in one timeline, oldest first, each with who wrote it, when, and what a review decided (a click on its age opens it on GitHub). It reads the newest 30 comments, 30 reviews and 30 threads of 10 comments, and says how many older ones are on GitHub. A box at the end posts a comment, with the Comment button or Ctrl+Enter (⌘Enter on macOS), through `gh pr comment` on the session's own machine, as its account there, which the box names; then the PR is read again to show it. Replies in threads, and reviews, stay on GitHub. It reads GitHub through `gh` (see Source control): this machine's when it is signed in to the repository's host, as that needs no ssh, else the session machine's; a repository this machine's account can't see is read from the session's machine until Refresh. A branch's PR is the newest one from the repository itself, an open one first; a fork's PR with the same branch name doesn't count, and when the 5 newest PRs from that branch name are all forks', the surface says so. The session's default branch, or a checkout on no branch, has none. One GraphQL query reads it, every 30 seconds while the surface shows, when the session's turn ends, and on Refresh; the PR's detail is read again only when it changed or its checks run. Nothing is read while the surface's tab isn't the one shown, the panel is hidden, or the window doesn't have the focus; on coming back, it reads at once if the last read is 30 seconds old. When a read fails, the surface keeps what it read before and says why above it. When GitHub's API limit for the account has 50 or fewer points left, polling waits for it to reset, and the surface says so and within how many minutes. Refresh reads it all again, and checks `gh` again when no machine could read.

Under the checks, an open PR offers to merge, in the way the account last chose where the repository allows it, with the repository's other ways in the button's menu, and to convert it to a draft; a draft offers Ready for review. A merge asks to confirm, merges only the head commit the surface showed when it was asked for (the session may push more since), and doesn't ask to delete the branch, which a session may still work on (a repository set to delete head branches on merge still does); a PR that conflicts with its base can't merge, and says so. These run `gh pr merge`, `gh pr ready` and `gh pr ready --undo` as the comment box does, on the session's machine, then read the PR again; when `gh` refuses, the surface says what it said.

A session can follow more PRs than its branch's: Link (the chain at the top) takes a PR's URL, `owner/name#N`, or `#N` or `N` in the session's repository, also a fork's PR, and opens it in a Pull request tab of its own, after the others; a number with no PR says so. Each Pull request tab is named for its PR's number, as `#12`, the branch's first (named Pull request until its PR is found). Unlink (beside Link), or × on a linked PR's tab, unlinks it and closes its tab. Closing the branch's tab closes the linked PRs' tabs too, which stay linked and open again with it. Links are kept between runs.

In the sidebar, each active session's row marks its PR after the branch (its branch's, else the first PR linked to it): the icon of its state, its number, and a red dot while its checks fail. These are read with one GraphQL query of each machine's sessions per host, without their details, when a session comes into the list and every 5 minutes while the window has the focus; the session on the Pull request surface is read by the surface instead.

Background work lists the session's running work, each with a button to stop it, then what ended, newest first, as the title bar's list does; a subagent's row opens its session. Under each run it lists the runs that one started, from the daemon's job list: a workflow's agent nodes, or a subagent's own subagents, each with its state, place in line, or error, and each subagent's row opens its session.

Pinning, settling and snoozing sessions is rho-ui's own idea; rho has no such state. Sessions started or continued in rho-ui list as active. Sessions from elsewhere, such as rho's terminal UI, start out settled, so the sidebar doesn't fill with old history; a session with work under way always lists as active, and pinning, snoozing, restoring, prompting, or steering one makes it rho-ui's. rho-ui keeps this in its [state database](architecture.md#state). A settled session comes back when it has new activity in rho-ui, and a snoozed one when its time is up. Snoozed and Settled sit under the active sessions, folded; open one to see its sessions on one line each, and hover a session for its details. An opened shelf shows its newest 25 sessions; Show more under them adds 25 more each time, and folding the shelf goes back to 25.

Settings (Ctrl+, or the gear at the bottom of the sidebar) open in a dialog over the window and hold the theme, the UI scale, the UI font (default Noto Sans) and the code font (default JetBrainsMono Nerd Font), saved in `$XDG_CONFIG_HOME/rho-ui/settings`. The theme is dark by default, or light, or whichever the desktop uses (System), following it as it changes. System isn't the default because on Linux rho-ui starts before the desktop portal reports light or dark, so a dark desktop would see a light first frame, and a desktop with no portal would stay light. Both themes are rho-ui's own, in `crates/rho-ui/themes/rho-ui.json` (GPUI Kit's theme format), in place of Kit's stock ones.

A mouse wheel's notch glides over about a quarter of a second rather than jumping, and a touchpad swipe carries on and slows after the fingers lift. Smooth scrolling in Settings says whether they do: On, Off, or System, the default, which is on unless the desktop asks for reduced motion. On Windows that is Settings → Accessibility → Visual effects → Animation effects: with it off, scrolling jumps until Smooth scrolling is On.

Source control shows the forge CLIs each machine has, so far GitHub's `gh`: its version and where it was found, and every account it is signed in to, with whether GitHub takes its token. rho-ui finds `gh` on the `PATH` its scripts run with, else through your login shell, as an ssh command may lack the `PATH` a terminal has; Program sets it instead, as an absolute or `~/` path, or a name on the `PATH`, saved in `$XDG_CONFIG_HOME/rho-ui/settings`. A Machine picker heads the page when there are remote machines, as each has its own `gh` and sign-ins. Signing in asks questions in a terminal, so an account that needs it offers `gh auth login` to copy; a token from a variable such as `GH_TOKEN` has to change where it is set, since `gh` prefers it. rho-ui runs `gh` without a login shell, so a variable such as `GH_TOKEN` or a proxy set only in a login profile doesn't reach it: on this machine, `gh` gets the environment rho-ui started with, from the desktop session; on a remote one, set it in a file an ssh command's shell reads, such as `~/.zshenv` for zsh. An account whose host couldn't be reached says so rather than asking you to sign in again; a check that takes over 60 s says so too. Opening the page checks the machine's CLIs if nothing has since it connected, and Refresh checks again; nothing checks them on a timer.

Providers lists the auth profiles each machine's rho can run sessions on (`rho/auth/list`): those signed in, each with Sign out, then those that take an API key, each with a masked box and Save, then those that take an account's login (such as ChatGPT's or GitHub Copilot's), each with Sign in. A machine's rho keeps its own sign-ins, so a Machine picker heads the page when there are remote machines. A profile counts as signed in when rho has a credential for it, saved or in the environment rho-ui gives its sessions, where it can't be overwritten or signed out from here; rho says which variable holds it. Sign in starts the login in the daemon, which runs it; rho-ui opens its page in the browser (only an `https:` page: a remote daemon names it), and shows the page, with a button to copy it, and any code to enter there, until the provider approves it or Cancel stops it. On this machine the provider's page sends the browser back to the daemon here; a remote machine's daemon couldn't be reached that way, so it signs in with a device code, which any browser can take, where the provider has one; for a provider without, the prompt says to sign in on that machine or use an API key. One machine runs one login from here at a time. A new sign-in reaches every session at once, and running ones from their next message. The page also says where rho keeps credentials, its credential store: the OS keyring (the Secret Service on Linux, the Keychain on macOS) or a file in the rho home, and what chose it; the page can change it, which rho saves in its config; that matters most when rho can't reach the OS keyring, as a daemon started over ssh, without a session D-Bus, can't reach the Secret Service. `RHO_CREDENTIAL_STORE` in rho's environment chooses it instead, and the page says so. Nothing tells rho-ui of a sign-in made in a terminal, so the page reads the profiles again each time it opens and when another machine is picked.

Worktrees lists the git worktrees each machine's rho added for sessions (`rho/worktree/prune` with `dry_run`), grouped by the project each came from. Each is named by its session's title, with its branch under it, or by its branch when there is no title to show: the session is gone or untitled, or rho-ui couldn't read which session it was (the prune names a worktree's job, so rho-ui finds the session in `rho/job/list`). Beside each is what a prune would do with it: remove it, once it is clean, merged into the current `HEAD` of the checkout it came from, and its session is neither loaded nor running, or keep it and say why: in use, uncommitted changes (flagged), not merged into that `HEAD`, or git's error (flagged). Those that need you lead their project, and one untouched for 14 days says so. A line heads the page with how many can be removed, and Remove prunes them as `rho worktrees prune` does, keeping each branch; the daemon checks each again, so the line then says how many it removed, and those leave the list. Opening Settings checks this machine's, picking a machine checks that one's, and the button beside the title checks again. A machine's rho keeps its own worktrees, so a Machine picker heads the page when there are remote machines.

After rho-ui's own pages comes rho's: one page with a group for each category of settings rho's daemon describes (`rho/config/schema`), in its order, each listed under it in the sidebar, saved in that machine's `~/.rho/config.toml`. rho-ui draws them from the daemon's description alone, so a setting a newer rho adds shows up with no change to rho-ui. Each item is the setting's name, what it does and when a change applies (from the next turn, to new sessions, or once rho restarts), with a control for its kind: a switch, a dropdown of its choices, a number box held to its range with its unit, or a text box. Number and text boxes apply on Enter or when they lose the keyboard; an empty one resets the setting. A model setting shows its model, which `/config` in rho's terminal UI changes, and a kind rho-ui doesn't know is left out. A setting your file sets can go back to its default with the page's reset button. A change applies at once and shows at once; rho-ui sends one write at a time to each machine. If someone else changed the settings since rho-ui read them, in rho's terminal UI or by hand, rho refuses the write: the page says your change didn't land and shows the settings as they are now. Changes made elsewhere show up on an open page as they happen. When `config.toml` doesn't load, the page says why, beside the setting it names, and rho uses the last values that loaded.

Every machine's rho has its own `config.toml`. With remote machines, a Machine picker heads rho's page, set to this machine when Settings opens; picking another shows that machine's settings. A machine that is connecting or can't be reached says so in place of its settings.

Last comes About: rho-ui's version, a link to its source and its license, then the version of Rho on each machine, or that it is connecting or can't be reached, with what that machine's rho needs under it, as the sidebar offers it (see [Installing and updating rho](#installing-and-updating-rho)).

rho-ui's own settings stay in its own file, not in rho's: the theme, scale and fonts must apply before the first frame, before any daemon answers, and the machines list is how rho-ui finds the remote daemons in the first place.

## Surfaces

rho's `ui` tool shows you a form or a small panel, an [A2UI](https://a2ui.org) surface, and can wait for you to act on it. rho-ui draws the surface in the transcript, under the run of tool calls that holds its `ui` call. It stays there and stays usable after the call returns and after the turn's working folds. A later call that updates the surface moves it under that call, and a surface the agent deletes leaves the transcript. A session opened again draws its surfaces the same from the daemon's replay; one that fell behind keeps them as they were, the tab you picked included.

Edits go to the surface's data model as you make them, so its checks update at once: a check that fails shows its message under the control, and a button whose own check fails is disabled, with the reason as its tooltip. Pressing a button whose action is an event sends it to the session, with what you entered, and returns the keyboard to the composer. A waiting `ui` call returns the action; otherwise the model reads it at its turn's next boundary, or in a turn rho starts for it. A button that opens a link opens it in your browser. If the session no longer has the surface, as it may not after its daemon was updated, the surface says so under itself, with what rho said, and takes no more actions. A surface too large to draw, past 2,000 components, stops where it is cut off and says so. If rho-ui can't apply part of a surface, because its A2UI is newer, the surface says that too.

Each component of the A2UI basic catalog has a form:

| Component | Drawn as |
| --- | --- |
| `Text` | Markdown, as a reply's text is; a caption is small and muted |
| `Row`, `Column`, `List` | Layout, placed as `justify` and `align` say. A row wraps when its children don't fit, and its inputs share its width. A row that says nothing lines its children up along its bottom edge, so a button sits level with the field beside it |
| `Card` | A bordered group, at most 36 rem wide |
| `Button` | A button: filled for `primary`, outlined by default, and a link for `borderless` |
| `CheckBox` | A checkbox |
| `TextField` | A text box under its label: one line, several lines that grow with the text, a number box with steppers, or dots with a button to show them. Text that is not a number stays out of a number field's data, and the form's buttons that send wait until it is fixed |
| `DateTimeInput` | A date picker, with the time of day beside the calendar when the field takes one, or a time field alone. Dates are kept as `2026-01-31`, times as `09:30`, both as `2026-01-31T09:30` |
| `ChoicePicker` | Radio buttons for one choice, checkboxes for several, or a row of toggle chips. The `filterable` option is ignored |
| `Slider` | A slider with its value beside it |
| `Tabs` | A tab bar over the tab that shows |
| `Modal` | A button that opens the content in a dialog |
| `Icon` | The matching icon; a dashed square for a name without one |
| `Divider` | A rule, across or upright |
| `Image` | The picture, at the size and fit it asks for, when its URL is a `data:` URL; an avatar is round. rho-ui loads no other URL, which shows as a chip, as a video's does |
| `Video`, `AudioPlayer` | A chip with the description that opens an `http` or `https` link in your browser |

The controls are the app's own, so the keyboard reaches them as it reaches the rest of the app.

## Installing and updating rho

rho-ui checks each machine's rho when it connects to it, or fails to, by running `rho update --check --json` there, over ssh for a remote machine. A check that found rho is good for an hour, since each one asks GitHub, which allows 60 requests an hour from one address without a login. A `rho` given as plain `rho` that isn't on `PATH` falls back to `~/.local/bin/rho`, where rho's install script puts it (on Windows, `%LOCALAPPDATA%\Programs\rho\bin\rho.exe`, where its PowerShell installer does), since a desktop session's or an ssh command's `PATH` often lacks that folder.

- No rho on this machine, and so no daemon to connect to: the main pane offers Install Rho in place of the connection's error, which runs rho's install script (`https://matthewyjiang.github.io/rho/install.sh`) into `~/.local/bin`, or into the folder of a `--rho` path, then connects. On Windows it runs rho's PowerShell installer (`install.ps1`) instead, into `%LOCALAPPDATA%\Programs\rho\bin` or the folder of a `--rho` path. A remote machine without rho gets the same offer at the bottom of the sidebar, into the folder of its rho path in Settings. A machine whose daemon answers has rho, wherever the check looked, so it is never offered an install.
- A newer release: the sidebar's footer says so with Update, which runs `rho update`, so rho installs it the way it was installed. When that needs a terminal, as pacman's `sudo` does, the footer shows the command to copy instead.
- After an update, the daemon still runs the old rho until nothing would be cut short. While it waits on work, the footer says how many things it waits for, with Restart now. rho-ui asks the daemon about a waiting upgrade when its jobs change, at once after it updates rho, and otherwise every 30 seconds, since the daemon's status reads its credential store each time. That restarts the daemon at once, stopping its background processes. Once it is back, rho-ui follows every session it had open again, in the same views, so what you typed in a composer stays: rho carries on a turn the restart cut short when a client that takes turns the daemon starts attaches to its session again. Sessions other clients follow, such as rho's terminal UI, are theirs to carry on.

A rho from before `rho update --check` can't say whether a newer one is out, so rho-ui offers nothing for it; update it once with `rho update`.

## Machines

rho-ui shows the sessions of several machines side by side: this one, and any remote machine you add on the Machines page of Settings by its SSH host, such as a host in `~/.ssh/config`. rho-ui reaches a remote machine over ssh, starts its daemon there if none runs, and runs its sessions with that machine's login environment. It does so with an ssh client of its own, the same on Linux, macOS and Windows, which follows your ssh config as `ssh -G` reads it: the host's name, user and port, your key files and certificates (`IdentityFile`, `CertificateFile`, and `IdentitiesOnly`), your key agent (`IdentityAgent`, else `SSH_AUTH_SOCK`; on Windows, else OpenSSH's agent; Pageant isn't used), and your `known_hosts` files (`UserKnownHostsFile`, `GlobalKnownHostsFile`, `HostKeyAlias`) and `RevokedHostKeys`. A host you reach through `ProxyJump` or `ProxyCommand` can't be reached yet, and says so. rho-ui can't ask for a password or a passphrase: it signs in with your key agent's keys and certificates, those of your configured files first, then with key files that have no passphrase, each with its certificate (`<file>-cert.pub` beside it, or a `CertificateFile`) before the bare key, so user certificates, such as Teleport's, Vault's or step-ca's, sign in from the agent or from files; an RSA certificate signs in only from the agent. A key file that has a passphrase is skipped, and the error names it, to add to your agent with `ssh-add`; so is a key file rho-ui can't sign with, such as a FIDO (`sk-`) key, and one whose name uses `%i`. Nor can it ask whether to trust a host: the host's key must already be in `known_hosts`, which rho-ui never changes, so run `ssh HOST` once in a terminal to check and accept it. A key that differs from the one listed stops the connection, and the error names the file and line, as does one your `RevokedHostKeys` file lists; a `RevokedHostKeys` that isn't there or that rho-ui can't read (it reads a text list of keys, not a KRL) stops every connection, as OpenSSH does. rho-ui reads that file as a text list of keys; one it can't read, such as a binary KRL, stops the connection and says so. rho-ui doesn't check host certificates yet: a host your `known_hosts` vouches for only with an `@cert-authority` line is refused, and the error says so; add the host's own key to reach it. With 1Password's agent you approve the key once per machine, and once more for its terminals: rho-ui keeps those two ssh connections while it uses the machine, and each for 10 minutes after, so a retry or reconnect asks nothing. A machine you remove in Settings lets its connection go 10 minutes later. A remote terminal keeps the terminals' connection open while it runs. A remote machine whose `rho` isn't on the `PATH` of an ssh command gets its rho path set on the same page, as an absolute or `~/` path. Each machine also has a clone folder there, where the project list clones repositories. Each machine has a name, set there too (this machine's is `local` until you change it; a remote one shows its host until named).

The sidebar lists every machine's sessions in one list, newest first, and with more than one machine each active row names its machine's label; a snoozed or settled row leaves it to the card its hover shows. The filter beside the search hides machines, or keeps to the projects you choose. A machine rho-ui can't reach shows at the bottom of the sidebar with ssh's or rho's reason and a Retry button; the others work on. A link that dies, as when the laptop sleeps or changes networks, shows there within about 45 seconds, when the ssh connection's keepalives give up. A login shell that hasn't printed its environment within 30 seconds fails the connection too.

Open sessions stay open while their machine's connection comes and goes. A session the daemon stops sending, because rho-ui fell behind, picks up where it left off, keeping its scroll position and what you unfolded. When the daemon restarts in place, as it does to upgrade, each open session says it is reconnecting, and carries on once the daemon is back; what you typed stays in the composer, and a message you sent as the daemon went goes again once it is back, and runs once. A connection that ends any other way, as when the daemon was stopped or the link died, leaves each open session saying so, with what it showed and what you typed: Retry in the sidebar follows them again. A message you sent as it went goes back in the composer, as does one you stop before the daemon is back. rho-ui never reconnects by itself then, unless it expects a restart because an upgrade waits, as it can't tell a restart from `rho daemon stop`. A session that is gone once the daemon is back, as one another client deleted, or a new one whose first message the restart cut off, which rho saved nowhere, keeps what it showed and says why, and the message goes back in the composer.

A remote machine needs a few things of its server:

- sshd must allow forwarding to a Unix socket, since rho-ui reaches the daemon through one, as `ssh -W` does. `AllowStreamLocalForwarding no` or `DisableForwarding yes` in `sshd_config` refuses it.
- rho there must report its daemon's socket in `rho daemon status --json`, as rho 3.1 does: rho-ui connects to the socket it names.
- The login shell must take `-l -c`. bash, zsh, fish and sh do; csh and tcsh may not.
- rho-ui starts the daemon from its ssh connection. Where systemd-logind has `KillUserProcesses=yes`, the daemon dies with that connection: when rho-ui quits, the link drops, or 10 minutes after rho-ui last used the machine; run `loginctl enable-linger` there, or start the daemon some other way.
- The daemon's home comes from `RHO_HOME` as an ssh command sees it, not as a login shell does. Set it in a file a non-login shell reads, such as `~/.zshenv`, if you move it.

A project is one repository, however many machines hold a checkout of it and whatever branch each is on. With more than one machine, the button in the project list's footer chooses the machine the session runs on: the list shows each project's checkout there, and a project with no checkout there shows where it is, with Clone to that machine: choosing it clones the repository from its origin remote into the machine's clone folder and starts the session in the clone. A project outside git, which has nothing to clone, shows dimmed, and choosing it looks for the same path on the chosen machine. Right-clicking either removes it. Each machine's clone folder is set on the Machines page; empty means `$RHO_HOME/projects` on that machine, and a relative path is from its home. git never prompts during a clone: a repository that needs a password, or a host key not yet known, fails with git's message, so the machine needs its own key for a private repository. Its ssh runs with `BatchMode`, unless on this machine you chose another ssh with `GIT_SSH` or git's `core.sshCommand`, such as PuTTY's `plink`, which rho-ui leaves as it is. A folder that already holds a clone of the same URL is taken as it is, once it has a commit; one a clone cut short left is refused as incomplete. Switching machines moves the draft to its project's checkout on the new one, else to that machine's home folder; a machine that isn't connected can't be chosen. Projects match by repository name without its owner, or by folder name outside git, so forks and same-named folders count as one. A typed path on a remote machine is browsed over the ssh connection to its daemon, once typing pauses; if its folders can't be read, the list says why and offers nothing to add. A file that would go by its path can't be attached to a message for a remote machine, and the refusal says why it would, such as its size over a limit: send text files and images there instead. A remote workspace's project name and branch come from running `git` there, over the ssh connection to its daemon, while it is connected; without `git` on that machine's `PATH` they show the folder's name and no branch. If its repositories can't be read, the sidebar's footer says why.
