# Features

How rho-ui behaves, in detail.

The composer's footer holds the session's settings: the permission mode (which tool calls run without asking) on the left, and on the right one button naming the model and reasoning, which opens the model list with search beside the reasoning levels and fast mode. New session opens the session right away, so these can be set before the first message; rho writes no file for a session until its first prompt, and the daemon discards an unused draft's session, so nothing is left behind. A setting changed while a turn runs applies when the turn ends.

A new session (Ctrl+N) starts in the project of the session on screen, else where the last new session started, else `DIR`. Above the draft's composer, "Start a session in" lists your projects, the most recently used first, with the draft's project checked; click one to move the draft there. rho-ui finds no projects on its own: you add them. Type an absolute or `~/` path in the search to browse folders: the list shows the folders the path can go on to (choose one to go into it), and a folder that is there offers Add. Add project… opens the desktop's folder chooser on this machine, and starts the search at `~/` on a remote one. Paste a git URL (`https://…`, `ssh://…`, `git@host:owner/repo`) and the list offers Clone, as does the footer's button in place of Add project…: Enter clones it into the machine's clone folder, adds the clone to your projects, and starts the session there. A URL of a repository the machine already holds lists its checkout instead. A project is a folder, and for a git repository its main checkout, so adding a linked worktree or a subfolder adds the repository it belongs to, and sessions in its worktrees count toward its age. Hover a project and click × (or right-click it) to remove it from the list; its folder stays. rho-ui keeps the list in its [state database](architecture.md#state). Ctrl+Shift+N starts a session with the keyboard in the list's search, which filters by name or path. In a git project, the button beside Add project… chooses where the session works: Local, the project's checkout, or New worktree, a git worktree that the rho daemon adds on a new `rho/…` branch from `HEAD`, so sessions in one repository don't write the same files. Choosing it makes nothing: the worktree is added when the first message goes, so switching back and forth leaves none behind. The draft's own session, which holds its settings, works in the checkout; the first message opens a session in the new worktree, gives it the draft's settings, and runs there. The daemon owns the worktree: it removes it once it is clean and merged, keeping the branch. `rho worktrees prune` removes those it can now. A session's directory is fixed once it opens, so moving the draft lets its session go and opens another in the new folder: the composer's text stays, and the settings start over from the new session's.

Type `/` at the start of a message, or `$` anywhere in it, and a menu above the composer lists the session's slash commands or skills that start with what you typed. The daemon lists them: rho's own commands it runs (`/compact`, `/init`, `/create-agent`), prompt templates, MCP prompts, workflows and agents, and the skills the session can load. Up and Down move the highlight, Tab completes, and Enter completes unless the name is typed out, or reads as an amount such as `$20`: then Enter sends. Escape closes the menu, without stopping a turn. A completed name goes as typed, and rho runs the command or loads the skill. Commands rho's terminal UI runs itself, such as `/model`, aren't offered.

While a turn runs, Enter in the composer steers it: the text joins the turn's next model request. Until the model reads it, it waits above the composer, where you can take it back. A message the turn can't take (it waits on an answer, or the daemon had just begun a turn of its own) waits above the composer too, and goes as the next prompt once the turn ends.

When a turn needs you, its request shows in a card above the composer, the oldest first, with a count of any behind it; it takes the keyboard if the composer is empty, so Enter answers. An approval offers Allow once, Allow for this session, and Deny, beside a box for a reason to deny: the tool reads it, and Enter there denies. A plan approval shows the plan and offers each permission mode to carry it out in, and Keep planning, beside a box for feedback that the model reads with whichever you pick. Questions the agent asks, or a subagent asks through its parent, are a questionnaire, one question at a time: pick one choice or several, type an answer of your own where the question takes one, skip an optional question, and submit, or decline them all. A choice the agent suggests is picked already, or marked "suggested" where it only points at it. An answer that doesn't reach the daemon leaves the card as you filled it in. If rho's `[questionnaire] timeout_seconds` is set, a question can come with a fallback: the card counts down to when rho answers it with the agent's fallback answers, and says what they are and why, and the count of requests behind the card counts down to the soonest of theirs. Your first key, paste or click in the card stops its countdown (`rho/session/hold`), and the question waits for you. A question rho answered at its deadline leaves a note in the transcript saying what it answered. The countdown reads the deadline by this machine's clock, so a remote machine's clock that is off shifts it. rho-ui opens its sessions with the questionnaire tool, so their agents can ask.

Each tool call shows the card rho's terminal UI draws for it, which the daemon sends with the call: one line naming the call, such as `read_file(src/main.rs)` or the command it ran, with short facts after it (`32 lines`, `13 matches in 2 files`, `+4 −1`, a nonzero exit). It opens into what the card shows: a search's matches, a command's output, a checklist, an error, an edit's diff. What the call returned to the model and no person needs, such as a whole file it read or an edit's receipt, stays hidden. A diff names its files from the session's workspace, and a diff of one file leaves out its header, as the call's line names the file. While a turn runs, its folded row of steps shows the step running now; opened, the row sums itself up instead, as that step is listed right below.

Messages draw a ` ```mermaid ` block as a diagram and `$$ … $$` or `$ … $` as a formula, in the theme's colors and font, redrawn when the theme or text size changes. Diagrams come from [pele](https://github.com/obsidianmd/pele), Obsidian's Mermaid renderer, run in an embedded QuickJS; formulas from [RaTeX](https://github.com/erweixin/RaTeX). A diagram wider than the transcript scales down to fit. A diagram shows as its code until its closing fence arrives, so a streaming reply doesn't redraw it with every chunk. What can't be drawn stays as written: a diagram pele can't read shows as code, and so does one that takes over 1 s or 64 MiB to draw (rho-ui says so on stderr); a formula RaTeX can't lay out shows as its source, and dollar signs read as prices ("$5 and $10") stay prose.

Attach any file with the paperclip at the left of the composer's footer, by dropping it on the composer, or by pasting it (Ctrl+V) after copying it in a file manager; paste an image the same way. Each shows above the composer's text: an image as a tile, any other file as a card. Hover one to remove it, or press Backspace in the empty text box to remove the last. They go with the text as one message, text first, as rho's terminal UI sends them, and the transcript shows them above the message's text.

What goes depends on the file. A PNG, JPEG, GIF or WebP image goes as an image the model sees. A text file of up to 200,000 characters (what the terminal UI sends of a document it attaches) goes whole. Any other file, such as a PDF or a binary, or a longer text file, goes as its path, and the agent reads it with its own tools; its card says "Sent by path". Attachments in one message can come to 16 MiB once encoded, images counting a third more as base64: the daemon reads a message as one line of at most 16 MiB (`rho_protocol::MAX_LINE_BYTES`). A steer carries only text, so a message with attachments sent while a turn runs waits above the composer and goes as the next prompt once the turn ends, and so does any message sent after it.

Background work a session's turns started (processes, workflow runs, subagents) is listed above the composer while it runs, with a button to stop each one. A turn ends while its background work runs on: rho-ui opens sessions with `idle_wake: turn`, so when the work finishes the daemon starts a turn of its own that gives the model the result, and rho-ui shows that turn like any other. Work leaves the list as it ends. A button in the title bar, counting what ended, opens the session's ended work, newest first, with how each piece ended (its exit status, failed, or stopped); it keeps everything rho-ui saw end, after the model has its result and across restarts. The daemon forgets work once the model has its result, so rho-ui records the work it sees start and end. Work it saw running that ended while it was closed shows as ended, with no word on how; work that started and ended while it was closed doesn't show.

Click a subagent's row, in either list, to open the subagent's own session, nested under the session that started it: the title bar reads `project / session / subagent's task`, and a click on any step above the last goes back to it. rho-ui observes the session (`rho/session/observe`) rather than attaching to it, as only the subagent writes there, so the view shows its messages and tool calls as they come, with no composer and no approvals (a subagent's questions go to its parent). A subagent of a subagent nests one step deeper. When the run ends, the parent shows the subagent's whole result as a card, its Markdown rendered and cut to its first 12 lines; Show more under it shows the rest, and Show less folds it again. Any card rho sends, such as a finished command's, shows the same way. Once the run ends, the daemon stops sending its events and the view keeps what it showed; opening the row again reads the session afresh. The sidebar lists only the session at the top, and marks it while one of its subagents is on screen.

The title bar shows the session's project and its title. Branch and other git details are not in it.

The sidebar lists the daemon's saved sessions. Once a second it also asks the daemon which sessions have work under way, so a session that runs a turn or waits for an approval shows as working or waiting whichever client started it.

The button at the top left of the sidebar, or Ctrl+B, collapses it to a narrow rail and opens it again. The rail keeps that button and Settings where they were and puts New session under it. While any session waits for an approval or runs a turn, the rail shows its status icon, so collapsing hides no session that needs you: hover the icon to see how many, and click it to open the sidebar. rho-ui remembers whether the sidebar is collapsed.

The panel at the right of the window holds surfaces, tools that sit beside the session. The toggle at the right end of the title bar, or Ctrl+Alt+B, shows and hides it; while it shows, the toggle sits at the same place in the panel's header. Drag its left edge to resize it, as far as leaves the session 30 rem (480px at the default scale) and no narrower than 16 rem; double-click the edge for its default width, 24 rem. rho-ui remembers whether it shows, and its width. With no surface open, the panel lists the surfaces to open, with those still to come (Terminal) dimmed under them; while one shows and another has no tab, + in its header opens a menu of them. Each surface opens as a tab; hover one and × takes the place of its icon to close it. Drag a tab onto another to move it there. The panel belongs to the window, not to a session: its tabs stay as you switch sessions, and each surface shows the session on screen. There are two surfaces so far.

Diff shows the uncommitted changes in the repository the session works in: every change to tracked files against `HEAD`, staged or not, and each untracked file that `.gitignore` doesn't leave out, as a new file, with how many files changed and lines added and removed. It runs `git` on the session's machine, over the ssh connection for a remote one, and reads the changes again when another session comes on screen, when the session's turn ends, and on Refresh; a read that finds the same changes leaves the view where it was scrolled. Changes made during a turn show once it ends, or on Refresh. A folder outside any git repository says so. A pull request's diff is for later, with GitHub's `gh`.

Background work lists the session's running work, each with a button to stop it, then what ended, newest first, as the title bar's list does; a subagent's row opens its session.

Settling and snoozing sessions is rho-ui's own idea; rho has no such state. Sessions started or continued in rho-ui list as active. Sessions from elsewhere, such as rho's terminal UI, start out settled, so the sidebar doesn't fill with old history; a session with work under way always lists as active, and snoozing, restoring, prompting, or steering one makes it rho-ui's. rho-ui keeps this in its [state database](architecture.md#state). A settled session comes back when it has new activity in rho-ui, and a snoozed one when its time is up. Snoozed and Settled sit under the active sessions, folded; open one to see its sessions on one line each, and hover a session for its details.

Settings (Ctrl+, or the gear at the bottom of the sidebar) open in a dialog over the window and hold the theme, the UI scale, the UI font (default Noto Sans) and the code font (default JetBrainsMono Nerd Font), saved in `$XDG_CONFIG_HOME/rho-ui/settings`. The theme is dark by default, or light, or whichever the desktop uses (System), following it as it changes. System isn't the default because on Linux rho-ui starts before the desktop portal reports light or dark, so a dark desktop would see a light first frame, and a desktop with no portal would stay light. Both themes are rho-ui's own, in `crates/rho-ui/themes/rho-ui.json` (GPUI Kit's theme format), in place of Kit's stock ones.

After rho-ui's own pages comes rho's: one page with a group for each category of settings rho's daemon describes (`rho/config/schema`), in its order, each listed under it in the sidebar, saved in that machine's `~/.rho/config.toml`. rho-ui draws them from the daemon's description alone, so a setting a newer rho adds shows up with no change to rho-ui. Each item is the setting's name, what it does and when a change applies (from the next turn, to new sessions, or once rho restarts), with a control for its kind: a switch, a dropdown of its choices, a number box held to its range with its unit, or a text box. Number and text boxes apply on Enter or when they lose the keyboard; an empty one resets the setting. A model setting shows its model, which `/config` in rho's terminal UI changes, and a kind rho-ui doesn't know is left out. A setting your file sets can go back to its default with the page's reset button. A change applies at once and shows at once; rho-ui sends one write at a time to each machine. If someone else changed the settings since rho-ui read them, in rho's terminal UI or by hand, rho refuses the write: the page says your change didn't land and shows the settings as they are now. Changes made elsewhere show up on an open page as they happen. When `config.toml` doesn't load, the page says why, beside the setting it names, and rho uses the last values that loaded.

Every machine's rho has its own `config.toml`. With remote machines, a Machine picker heads rho's page, set to this machine when Settings opens; picking another shows that machine's settings. A machine that is connecting or can't be reached says so in place of its settings.

rho-ui's own settings stay in its own file, not in rho's: the theme, scale and fonts must apply before the first frame, before any daemon answers, and the machines list is how rho-ui finds the remote daemons in the first place.

## Machines

rho-ui shows the sessions of several machines side by side: this one, and any remote machine you add on the Machines page of Settings by its SSH host, such as a host in `~/.ssh/config`. rho-ui reaches a remote machine over ssh, starts its daemon there if none runs, and runs its sessions with that machine's login environment. ssh can't ask for a password in the app: the host must be in `known_hosts`, and your key must sign without a terminal prompt, as an SSH agent does. With 1Password's agent you approve the key once; rho-ui keeps one ssh connection per machine for ten minutes after its last use, so a retry or reconnect asks nothing. A remote machine whose `rho` isn't on the `PATH` of an ssh command gets its rho path set on the same page, as an absolute or `~/` path. Each machine also has a clone folder there, where the project list clones repositories. Each machine has a name, set there too (this machine's is `local` until you change it; a remote one shows its host until named).

The sidebar lists every machine's sessions in one list, newest first, and with more than one machine each active row names its machine's label; a snoozed or settled row leaves it to the card its hover shows. The filter beside the search hides machines, or keeps to the projects you choose. A machine rho-ui can't reach shows at the bottom of the sidebar with ssh's or rho's reason and a Retry button; the others work on. A link that dies, as when the laptop sleeps or changes networks, shows there within about 45 seconds, when ssh's keepalives give up. A login shell that hasn't printed its environment within 30 seconds fails the connection too.

A remote machine needs a few things of its server:

- sshd must allow forwarding to a Unix socket, since rho-ui reaches the daemon with `ssh -W`. `AllowStreamLocalForwarding no` or `DisableForwarding yes` in `sshd_config` refuses it.
- The login shell must take `-l -c`. bash, zsh, fish and sh do; csh and tcsh may not.
- rho-ui starts the daemon from its ssh connection. Where systemd-logind has `KillUserProcesses=yes`, the daemon dies with that connection, ten minutes after rho-ui last used it; run `loginctl enable-linger` there, or start the daemon some other way.
- The daemon's home comes from `RHO_HOME` as an ssh command sees it, not as a login shell does. Set it in a file a non-login shell reads, such as `~/.zshenv`, if you move it.

A project is one repository, however many machines hold a checkout of it and whatever branch each is on. With more than one machine, the button in the project list's footer chooses the machine the session runs on: the list shows each project's checkout there, and a project with no checkout there shows where it is, with Clone to that machine: choosing it clones the repository from its origin remote into the machine's clone folder and starts the session in the clone. A project outside git, which has nothing to clone, shows dimmed, and choosing it looks for the same path on the chosen machine. Right-clicking either removes it. Each machine's clone folder is set on the Machines page; empty means `$RHO_HOME/projects` on that machine, and a relative path is from its home. git never prompts during a clone: a repository that needs a password, or a host key not yet known, fails with git's message, so the machine needs its own key for a private repository. A folder that already holds a clone of the same URL is taken as it is. Switching machines moves the draft to its project's checkout on the new one, else to that machine's home folder; a machine that isn't connected can't be chosen. Projects match by repository name without its owner, or by folder name outside git, so forks and same-named folders count as one. A typed path on a remote machine is browsed over the ssh connection to its daemon, once typing pauses; if its folders can't be read, the list says why and offers nothing to add. A file that would go by its path can't be attached to a message for a remote machine: send text files and images there instead. A remote workspace's project name and branch come from running `git` there, over the ssh connection to its daemon, while it is connected; without `git` on that machine's `PATH` they show the folder's name and no branch.
